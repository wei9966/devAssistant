# AI 智能助手升级方案

## 一、现状分析

### 1.1 当前架构
```
用户输入 → LLM理解意图 → 解析Function Call → 执行硬编码逻辑 → 返回模板化结果
```

### 1.2 主要问题

| 问题 | 具体表现 | 影响 |
|------|----------|------|
| 报表假智能 | 日报/周报是 Rust 硬编码模板，AI 只是触发器 | 输出固定，无个性化分析 |
| 单步操作 | 只能执行一个 Function Call | 无法处理"创建任务并开始番茄钟" |
| 浅层上下文 | 只记住上一个操作 | 无法引用历史对话 |
| 无润色闭环 | 查询结果需要二次 AI 调用润色 | 效率低，可能丢失上下文 |
| 无主动能力 | 只能被动响应 | 不会主动提醒和建议 |

## 二、升级目标

### 2.1 核心目标
将 AI 助手从 **"带自然语言界面的数据库工具"** 升级为 **"真正能思考的智能工作伙伴"**

### 2.2 量化指标
- 日报内容由 AI 真正生成（含工作洞察和建议）
- 支持单次对话执行 3+ 个连续操作
- 上下文记忆持久化（跨会话保留关键信息）
- 响应时间控制在 3 秒内

## 三、升级方案

### 3.1 Phase 1: AI 真正生成报表（优先级最高）

**目标**: 让 AI 根据数据生成有洞察力的报表，而非填充模板

**当前问题代码**:
```rust
// 硬编码模板 - ai_chat_service.rs
let mut content = format!("## 📅 {} 日报\n\n", date);
content.push_str("### ✅ 今日完成\n\n");
for title in &task_titles {
    content.push_str(&format!("- {}\n", title));  // 只是列表
}
```

**改进方案**:
1. `generate_daily_report` 收集数据后，调用 AI 生成报表内容
2. AI 分析数据，给出工作洞察（如：效率变化、建议等）
3. 保留数据准确性，但让表达更智能

**新架构**:
```
收集今日数据 → 构建分析提示词 → AI 生成报表 → 返回结果
```

**实现细节**:
- 新增 `generate_report_with_ai()` 函数
- 报表提示词包含：完成任务列表、专注时长、与昨日对比
- AI 输出格式要求：包含完成总结 + 效率分析 + 明日建议

### 3.2 Phase 2: 多步操作串联（Agent 模式）

**目标**: 支持用户一句话触发多个操作

**用例**:
- "创建一个高优先级任务'完成报告'，然后开始25分钟番茄钟"
- "把昨天没完成的任务都标记为今天待办"
- "删除所有低优先级的已完成任务"

**实现方案**:
1. 修改 Function Call 解析，支持返回操作数组
2. 实现操作队列执行器
3. 操作间支持上下文传递（如：创建任务返回 ID → 开始番茄钟使用该 ID）

**新的 Function Call 格式**:
```json
{
  "steps": [
    {"function": "create_task", "arguments": {"title": "完成报告", "priority": 1}},
    {"function": "start_pomodoro", "arguments": {"task_id": "$previous.task_id", "duration": 25}}
  ]
}
```

**关键设计**:
- `$previous.xxx` 语法引用上一步结果
- 失败处理：某步失败时，回滚或继续执行的策略
- 结果合并：多步操作的结果统一汇总返回

### 3.3 Phase 3: 深度上下文记忆

**目标**: AI 能记住重要的历史信息，跨会话使用

**实现方案**:
1. 新增 `ai_context_memory` 表存储关键信息
2. AI 主动提取对话中的关键实体和偏好
3. 系统提示词注入历史上下文

**数据库设计**:
```sql
CREATE TABLE ai_context_memory (
    id INTEGER PRIMARY KEY,
    context_type TEXT NOT NULL,     -- 'entity' | 'preference' | 'fact'
    key TEXT NOT NULL,              -- 如 'project:报告系统'
    value TEXT NOT NULL,            -- JSON 格式的详细信息
    importance INTEGER DEFAULT 1,   -- 重要性评分 1-5
    last_used_at TIMESTAMP,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```

**上下文类型**:
- `entity`: 实体信息（项目、人名、常用任务）
- `preference`: 用户偏好（工作时间、番茄钟时长偏好）
- `fact`: 事实（"周五要提交报告"）

**使用流程**:
```
用户输入 → 提取关键词 → 查询相关上下文 → 注入系统提示词 → AI 响应
```

### 3.4 Phase 4: 智能润色优化

**目标**: 减少 AI 调用次数，提升响应速度

**当前问题**:
1. 查询数据后需要二次调用 AI 润色
2. 润色时可能丢失原始上下文

**改进方案**:
1. 对于简单查询，使用模板化响应（不调用 AI）
2. 对于复杂查询，将数据和润色请求合并为一次调用
3. 缓存常见查询的润色结果

**决策逻辑**:
```
查询结果 →
  if 结果简单（<5条，结构化数据）→ 模板化响应
  if 结果复杂 → AI 润色
  if 有缓存 → 使用缓存
```

## 五、开发优先级

```
Phase 1 (AI生成报表) ──────► Phase 2 (多步操作) ──────► Phase 3 (上下文记忆)
        ↓                           ↓                          ↓
    体验提升明显              复杂操作支持              对话更连贯
    改动量适中                改动量较大                改动量中等
```

**建议开发顺序**: Phase 1 → Phase 3 → Phase 2 → Phase 4

Phase 1 效果最明显且改动可控，优先实现。

## 七、风险与对策

| 风险 | 对策 |
|------|------|
| AI 生成内容不准确 | 提供原始数据作为约束，要求必须基于真实数据 |
| 多步操作执行失败 | 实现事务回滚或部分成功提示 |
| 上下文过多影响性能 | 限制注入上下文数量，按重要性排序 |
| API 调用增加成本 | 智能决策是否需要 AI，简单场景用模板 |
